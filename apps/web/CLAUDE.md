# CLAUDE.md — Hartford Bound (`apps/web`)

Project guidance for Claude Code. This is the committed, shared conventions doc for the web app.

## Project shape — read this first

Hartford Bound is a **public, static** React SPA about Hartford's history of race, migration, and
mobility. A few facts shape every decision here:

- **There is no backend, and there never will be.** Content comes from **published Google Sheets
  CSVs** (read-only, no API key) — and by default from the **seed CSVs bundled in
  `apps/web/public/data/`**. The CSV fetch *is* the real data layer; there are no server stubs or
  `// TODO: replace with real backend` placeholders to swap in later.
- Stack: **Vite + React 19 + TypeScript (strict)**, **Redux Toolkit + RTK Query**, Tailwind v4,
  Mapbox GL, React Router (`HashRouter`).
- **Deploys to GitHub Pages** at `https://jbk13004.github.io/hartford-bound/` via
  `.github/workflows/deploy.yml` (builds `apps/web`, publishes `apps/web/dist`).
- **Package manager: yarn.** All web commands run from `apps/web/`.

## React / TypeScript Architecture — Redux Toolkit + RTK Query

Every feature lives under `apps/web/src/features/<feature_name>/` and is self-contained, with strict
separation between presentation, business logic, and data fetching.

### Feature folder structure

```
apps/web/src/
├── app/                 — store (configureStore + setupListeners)
├── shared/              — cross-feature code
│   ├── api/             — csvBaseQuery (the shared base query)
│   ├── config/          — sheets.ts (SHEET_URLS)
│   ├── components/      — Layout, Header, Footer, NotFound
│   └── types/           — shared/ambient types
└── features/
    └── stories/
        ├── components/  — presentational components (views)
        ├── hooks/       — feature-level hooks (controllers/orchestration)
        ├── state/       — Redux slices/selectors (only if cross-cutting UI state is needed)
        ├── api/         — RTK Query endpoints for this feature
        ├── types/       — raw CSV row + domain model + the row→domain mapper
        ├── __tests__/
        └── index.ts     — public surface of the feature
```

`stories/` is the reference feature; new features follow its shape.

### Use feature foldering
Organize by feature/domain, not by file type. Components, hooks, slices, endpoints, and types for a
feature live together. Cross-feature shared code goes in `apps/web/src/shared/`.

### Use RTK Query for all data fetching
Every data fetch goes through an RTK Query `createApi` endpoint built on the shared `csvBaseQuery`.
No raw `fetch` / `axios` in components or hooks. RTK Query provides caching, deduplication,
stale-while-revalidate, and the auto-generated hooks the views consume.

### Naming
- API files: `<feature>Api.ts` exporting a single `createApi` instance.
- Slice files (when needed): `<feature>Slice.ts`; selectors in `selectors.ts` as `selectXxx`.
- Hooks: camelCase, `use`-prefixed — `useStoriesList`, `useStory`.
- RTK Query hooks are auto-generated — `useGetStoriesQuery`, `useGetStoryByIdQuery`.
- Action creators are auto-generated by `createSlice` — do not hand-roll them.

### Slice vs local state — state tiering discipline
Walk this hierarchy in order:
1. **Fetched data** → RTK Query. Never store query responses in slices manually.
2. **Local-only ephemeral UI state** (search input text, modal open/closed, active tab, view
   toggle) → `useState` / `useReducer`. Never put these in Redux.
3. **Stable subtree values** (theme, locale, current context) → `useContext`. Never for
   frequently-changing values.
4. **App-wide domain/cross-cutting state** → Redux Toolkit slices.

If you reach for Redux to hold a form field value or a modal toggle, stop — that's a tier-2
violation. (As of today no feature needs a slice; the list/detail views are pure RTK Query + local
UI state.)

### BLoC discipline in Redux (when slices are introduced)
- BLoC events → actions named in past tense for user-driven events (`storyOpened`, not `fetchStory`).
- BLoC states → slice state shape; BLoC streams → `useSelector`; side effects → `createAsyncThunk`
  or RTK Query endpoints. Actions are the only mutation path.

### State design
- All slice state is fully typed; define a `State` interface at the top of each slice file.
- Use discriminated unions with a `status` field for state machines.
- Use `createSlice`'s Immer-backed reducers. Selectors are colocated and always used.

### Components (views)
- Pure presentational units. May hold **ephemeral UI state only** (input value, active tab, hover).
- No `fetch`, no validation logic, no side effects. Consume data via the feature's hooks (which wrap
  the RTK Query auto-hooks); render loading / error / data straight from them.

### Hooks (controllers)
- Feature hooks orchestrate state and side effects — the "controller" layer. They compose RTK Query
  hooks, `useSelector`/`useDispatch`, `useMemo`, and own derived state (filtering, sorting, deriving
  related items). They return primitives, plain objects, or functions — never JSX.

### Types and models
- Each feature's `types/` defines the **raw CSV row** (e.g. `StoryRow`, all strings) separately from
  the **domain model** (`Story`), with a `toStory(row)` mapper that parses values (`"TRUE"`→boolean,
  comma/pipe lists→arrays, string→typed union, etc.). Shared types go in `apps/web/src/shared/types/`.
- All types explicit. No `any` without justification — prefer `unknown` and narrow. Use `readonly`
  for immutable structures and `as const` for literal unions.

### Configuration
- The store is configured once in `apps/web/src/app/store.ts` (`makeStore()` builds it; the singleton
  `store` is provided via `<Provider>` at the root). Each feature API is registered there.
- Per-feature configuration is the **sheet URL**, which flows through `shared/config/sheets.ts`
  (`SHEET_URLS`) into the shared `csvBaseQuery` — not through component props. No separate DI
  container.

### Data layer: published Google Sheets CSV
The data source is **published Google Sheets CSV** — there is no backend, so there are no stubbed
`queryFn`s and no TODO placeholders. The CSV fetch is the real implementation.

- **One shared base query** — `shared/api/csvBaseQuery.ts` — fetches a CSV URL and PapaParses it
  identically for every endpoint (header rows, skip empty lines, trimmed headers; parse warnings are
  non-fatal and logged), normalizing errors to `{ status, data }`. Endpoints stay declarative
  (`query: () => SHEET_URLS.stories`) and own only the row→domain mapping via `transformResponse`.
  Reserve a custom `queryFn` for the rare endpoint that must combine multiple sheets.
- **Raw row vs domain model.** `transformResponse` maps the raw `CsvRow[]` (all strings) to typed
  domain objects via the feature's `toX` mapper. Keep the `XRow` and `X` types distinct.
- **Near-static caching.** Sheets change rarely, so each API uses `keepUnusedDataFor: 3600` and
  `refetchOnFocus / refetchOnReconnect / refetchOnMountOrArgChange: false` — a sheet is fetched about
  once per session, which makes the detail page's by-id lookup cheap.
- **Sheet URLs** live in `shared/config/sheets.ts`. Each defaults to the bundled seed CSV in
  `public/data/<name>.csv` (prefixed with `import.meta.env.BASE_URL` so it resolves under the Pages
  base too) and is overridable with a `VITE_SHEETS_*_URL` env var pointing at a published Google
  Sheets CSV — switching to live data needs no code change.

### Testing
- Vitest (jsdom) + React Testing Library, with MSW returning CSV text. Tests live in each feature's
  `__tests__/`. Query by role / accessible name, not test IDs.
- Cover: the `csvBaseQuery` parse/error behaviour, each API's row→domain mapping (MSW CSV →
  asserted domain objects), and major views (MSW-backed render). `src/test/` holds the MSW server,
  handlers, setup, and the `renderWithProviders` / `renderHookWithProviders` helpers
  (`makeStore()` gives each test an isolated store; the hook variant also wraps a router).
- **mapbox-gl does not render in jsdom.** To test a view/hook that uses it, `vi.mock('mapbox-gl', …)`
  returning `{ default: { accessToken, Map, Marker } }` (it's consumed as a *default* export), then
  import the component under test *after* the mock (`const { X } = await import('…')`) so the hook
  picks up the stub. Assert the derivation (markers built/filtered) via a fake `Marker`, not the GL
  DOM. See `features/home/__tests__/Homepage.test.tsx`.

### Enforcement
- Never put a `fetch` / `axios` call inside a component or non-API hook — all data I/O goes through
  RTK Query on `csvBaseQuery`.
- Never put JSX inside a slice, thunk, selector, or mapper.
- Never store fetched responses or ephemeral UI state in a slice manually.
- Never bypass `createSlice` to hand-roll action types/reducers.
- If a file is doing two jobs, split it.

## Build & Development Commands

All web commands run from `apps/web/`:

```bash
yarn install             # Install dependencies
yarn dev                 # Run dev server
yarn build               # Production build
yarn preview             # Preview the production build locally
yarn test                # Run all tests (vitest run)
yarn test:watch          # Vitest watch mode
yarn typecheck           # TypeScript check (no emit)
yarn lint                # ESLint
```

## GitHub Pages constraints

This site is a static GitHub Pages **project site**, which constrains a few things:

- **`base` must match the repo name.** `vite.config.ts` sets `base: '/hartford-bound/'` in
  production; if the repo is renamed, update it (and the Pages URL) or every asset 404s.
- **`VITE_*` vars are public.** They're inlined into the client bundle at build time and are not
  secret. `VITE_MAPBOX_TOKEN` is therefore protected by a **URL-restricted Mapbox token** (allowed
  origins include `jbk13004.github.io`), not by hiding it. The deploy workflow injects it from the
  `VITE_MAPBOX_TOKEN` repo secret.
- **`HashRouter` is intentional.** Routes carry `#/`, which means no `404.html` SPA fallback is
  needed — deep links and hard refreshes work on Pages with zero server config. Don't switch to
  `BrowserRouter` without adding a Pages SPA fallback.
- **Deploy** is the `.github/workflows/deploy.yml` GitHub Action: it builds `apps/web` and publishes
  `apps/web/dist`. One-time setup: Settings → Pages → Source = "GitHub Actions", and add the
  `VITE_MAPBOX_TOKEN` repo secret.
- `.claude/commands/deploy.md` (tag / RELEASE.md / Codemagic flow) is **obsolete** — superseded by
  this workflow.

## Working agreements

- **Plan first** for non-trivial work; if something goes wrong, stop and re-plan rather than pushing
  through. Prefer the simplest change that's correct; don't over-engineer.
- **Verify before declaring done** — `yarn build`, `yarn typecheck`, and `yarn test` should be green;
  exercise the change in the running app when behaviour matters.
- **No merges to `main` and no deploys without explicit approval.**
